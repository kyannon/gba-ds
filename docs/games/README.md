# Game rulesets

One file per supported game: what GBA DS shows on each screen, as numbered rules. They're the baseline for changing a game's profile (`src/profiles.c`): a change that breaks a rule is a regression unless the rule is changed with it, on purpose. `tools/regress.py` checks them against approved screenshots of real states (see [../TESTING.md](../TESTING.md)).

## General rules

**GEN-1. Logo.** A game's logo is taken from its own title screen (per release: `logo` cases check each one) and shown on the second screen before the first capture and wherever a game's rules say so. It's always shown as the game draws it: at its own size (one of its pixels per GBA pixel of the second screen, GEN-5), centred; with no logo, the game's name. When it's all the second screen shows (nothing live to show), it's at half strength on dark grey, so the screen reads as idle and its edges plainly match the game screen's. Under something live (a status bar or other HUD moved there, a title card's pieces, Mario Kart's podium) the second screen is black and the logo at full strength: a live second screen reads apart from an idle one, and the game's own fades to black (a pipe, a door) fade into it. (Until v1.3.2's later test builds, some games showed it smaller and dimmed behind their windows, and the others on black; until v1.4.11's later test builds a live second screen was dark grey too.)

**GEN-2. The game is never touched.** Captures run on a hidden second copy of the game from a copy of the live state; the game being played is never paused, sent input or changed by them (sprite hiding and HUD splits only change what's drawn). *By hand: the tests only see the screens; check on the device that games play the same with `map = 0` and with it on (the capture copy has its own core and state). (checked on the device for v1.4.2)*

**GEN-3. Nothing half-drawn.** A capture is only shown once its checks pass (memory flags and fixed pixels of the screen it opened); otherwise the last good picture stays.

**GEN-4. Same input, same pictures.** With `GBADS_SYNC=1` a run is deterministic, so the tests compare screenshots exactly. *By hand: checked by running the suite twice with no differences, after any change to capture timing (mapcap.c, logo.c, GBADS_SYNC). (checked with v1.5.1: the full suite run twice, locally and on GitHub, with no differences)*

**GEN-5. A GBA screen.** The second screen is a 240x160 picture like the game screen, scaled up the same way (Settings: Map Scale, as Scale is for the game screen), so with the same settings a GBA pixel is the same size on both screens: whatever a game puts there (a map, a status screen, a window, the logo) is at the game's own size. (Until v1.3.2's later test builds, Fire Emblem's, Final Fantasy Tactics Advance's and the Advance Wars games' second screens were bigger pictures, 320x240 or 512x384, so what they showed was smaller than on the game screen.) Mario Kart's race screen is the exception for now: its course map is drawn larger, and the scenery behind it smoothly scaled.

**GEN-6. Quick to follow.** When what a game's second screen is about changes (its profile's `room` probes: the cursor on another unit, Mario on another level, another room), a capture starts as soon as the change has held for 3 frames, without waiting for the regular refresh; one still running for the old place is called off. The hidden copy doesn't draw the frames it only waits through. *By hand: how soon the second screen follows on the device (the tests run captures inline, at fixed frames). (checked on the device for v1.4.2)*
**GEN-7. Saved with the state.** A state saved by GBA DS keeps what the second screen was showing (a capture with its pages, a copied screen, a level's name, Sonic Advance's zone card); loading it puts that back on the next frame, so the second screen matches the moment at once instead of waiting for the next capture or showing the logo. The game's own rules still decide whether it's shown (a state saved on the logo loads on the logo), and the next capture replaces it as usual. A state from before this (or from another emulator, or saved in another release of the game) loads as before, and whatever was kept from the last moment that only that moment can show (a zone card, a level's name) goes. Pinball's two-screen views and HUD pieces aren't kept: they're drawn again from the game within a frame or two.

**GEN-8. Say when a ROM isn't the game as released.** In the game list, the selected game's panel says, under the game's logo at the top right, when a supported game's ROM is a romhack it knows ("Romhack: Superstar Saga+ v1.5 (100%)", with "untested" after the name when the mod's tests don't run on that version) or a ROM it doesn't know ("Modified ROM: the second screen may not work"): patched, hacked, trimmed or a bad dump (see "Releases and dumps" below). An official dump, tested or not, says nothing. It's known once GBA DS has read the ROM, which it does in the background when the game is first selected (half a second or so on the device), then remembers it until the file changes; nothing is said until then.

**GEN-9. Patches, switched on in the game.** Patch files (`.ips`, `.ups`, `.bps`, `.xdelta`; an xdelta made with compression, xdelta3 `-S`, is listed as one GBA DS can't read) for a game go in its own folder in GBA DS's `patches` folder, named after the release as No-Intro names it ("Mario & Luigi - Superstar Saga (USA)"; for a game with no list of dumps, its ROM header's title and code), whatever the ROM file is called; GBA DS makes the folder when the game starts. The pause menu's Tools tab has **Patches**, which lists them with an On/Off switch each, as Cheats does: the patch's name and type ("Superstar Saga Plus (IPS)") and what GBA DS knows of it ("Tested romhack: Superstar Saga+ v1.5 (100%)", "Untested", or "Made for another version", which can't be switched on: a UPS or BPS whose checksum isn't this ROM's). Several can be on: they're applied in the list's order, the ones on at the top, numbered ("1. ..."), the rest below by name; a patch switched on goes last, and X (or a tap on its number) picks one up to move it with Up / Down (or a tap where it goes), A to put it down. With two or more applied, the list tries them together as the game will: a line under the folder's name says what they make together ("Together: Tested romhack: ..." / "Together: Untested"), a patch that can't follow the ones above it (a UPS or BPS is made for the unchanged ROM: it has to be first) shows "Fails" with a note to move it up and is left out when the game starts, and one that changes some of the same bytes as one above it has its name in gold and a note that they may not work together (the lower one wins there). Up to seven are on at a time. Switching one asks first ("Sure?", with a note to save the game first) and then restarts the game with the change (Y: not yet, for more changes first). When the change can't upset the game's saves (the patched ROM is the same size as the one playing, and the battery save and save states stay the same files: the "separate" switches off, or the change doesn't change their names), it doesn't restart: the game carries on from the very moment, with the change (the note says "carry on from here"; colours already on the screen change as the game draws them again). While what's chosen isn't what the game started with (switched for later, or moved), the list's top row says so, and A on it ("Sure?", A again) restarts the game with it; otherwise it's used from the next start. With patches on:
- the game, its second screen and its logo are the patched game's;
- by default it has its own battery save and save states ("<ROM name> + <patch name>"; with several, their names by name, " + " between, so moving them doesn't change it), so a romhack that changes the whole game doesn't load the original's saves; two switches at the top of the list, "Separate battery save" and "Separate save states", turn either off (a colour patch, say, can carry on from the original's save);
- RetroAchievements are off (they aren't allowed for patched games), and their banner at the start says so instead;
- a patch in `docs/patches.md` (known by its file's checksum, whatever it's called) is named in the list ("Known colour patch, tested: ..." / "untested"), and one made for another version of the game says so ("made for <dump>: this ROM is another version, it may break the game"), an optional patch on its main patch's result excepted; a known colour patch that changes colours the second screen looks for has them swapped in the profile (Metroid: Zero Mission's pause screen), so the second screen works as on the unpatched game;
- a save state made with another ROM than the one playing (other patches, none, or another dump; the state says, mGBA keeps the ROM's CRC32 in it) still loads, with a note that it may not work: "saved without the patches on", "saved with <a known dump or patch>", or "saved with another version of the game (other patches, or another ROM)"; the log says which (any state, from the slots, the quick bar, a hotkey or the resume at start);
- GEN-8 goes by the patched ROM ("Romhack: NAME (patch)", or "Patched: the second screen may not work"; "Patched, but a patch was left out" when one of them can't be applied where it is), and the log and bug reports name the patches applied, any left out, and the ROM file's own checksum.

A patch file beside the ROM with its name (`Mario & Luigi.ips` beside `Mario & Luigi.gba`), as RetroArch uses them, is always on, and shows in the list as "Always (beside the ROM)". A patch that can't be applied (made for another ROM, or not a patch) isn't: the game starts without it, and the list and the game list say why.

**GEN-10. Buttons, per game.** The pause menu's Controls tab has a row for each face button, by its name and where it sits, "A (right) button", "B (bottom) button", "X (top) button" and "Y (left) button", and for "L button", "R button" and the four D-pad directions ("D-pad up", "D-pad down", "D-pad left", "D-pad right"), each saying what it gives the game: GBA A, GBA B, GBA L, GBA R, GBA Up, GBA Down, GBA Left, GBA Right, Start, Select, Turbo A, Turbo B or Nothing. L, R and the D-pad give their own GBA button until changed. The list scrolls (a settings page shows 8 rows at once: the D-pad or a finger dragged moves it). LEFT / RIGHT (or A, or a tap) step through them: for this game with "This game" lit above the rows, for all games with Y or "All games" (settings in layers: `docs/MENUS.md`). Two face buttons can give the same value. The default is `ab_swap`'s (A (right) gives GBA A and B (bottom) GBA B, or the other way round with `ab_swap = 1`; X and Y nothing). A change is used straight away and kept in `states/<game>.cfg` (this game) or `states/prefs.cfg` (all games; `button_right`, `button_bottom`, `button_top`, `button_left`, `button_l`, `button_r`, `button_dpad_up`, `button_dpad_down`, `button_dpad_left`, `button_dpad_right`); a game with nothing of its own follows those, then `ab_swap`. A game's old `<game>.buttons` is moved into its `.cfg` the first time it starts. Only what the game gets changes: GBA DS's own screens keep A to choose and B to go back, L1 / R1 stay GBA L / R in them, and the hotkeys (HOME + X, HOME + Y) are as before. In the games with a layout picker under Controls in the quick bar (the SNES layout in Super Mario Advance 2 and 3, the four-button layout in Tony Hawk's Pro Skater 2 and 3), that layout decides the face buttons wherever it's used (the SNES one in levels; four-button always, or while skating with Auto), and these choices everywhere else; the Controls rows say so under them. The log and bug reports list the choices when they aren't the default.

**GEN-11. The player's own and scraped logos, at the game's logo's height.** A game's logo is, first, the player's own `logos/<CODE>` (`.png`, `.bmp`, `.jpg` or `.webp`); else, with `logo_folder` set (a folder of logos a scraper downloaded, as EmulationStation's or Skraper's), the image there whose name is the ROM file's, whatever type info either name has: everything from the first `(` or `[` is left out of both, and case doesn't matter, so `Golden Sun.png`, `Golden Sun (USA).jpg` and `Golden Sun-marquee.png` all go with `Golden Sun (USA, Europe).gba`, but `Golden Sun - The Lost Age.png` doesn't. Several matching: the ROM's whole name first, then the bare title, then the title with `-marquee`, `-wheel` or `-logo`, then with any other `-suffix` (box art such as `-image` last), PNG or WebP before JPG, then by name; a WebP image is read as one whatever its name ends in (scrapers save them as `.png` too), an animated WebP isn't read; else the extracted logo. An own or scraped logo is used wherever the extracted logo would be (the idle second screen, under a HUD, in fights, the game list), cut to what's drawn (a PNG's or WebP's transparent edges; a JPEG's plain border, the colour of its top-left corner, its background inside the logo's box kept; a PNG with no transparency is kept whole) and made as tall as the extracted logo (never wider than the GBA screen), so it sits where the game's own logo would and nothing around it moves. The extracted logo is the measure, so it stays as it is. Until it exists (or for a game with none to extract) an own or scraped logo fits a 224x64 box, and takes its size once extraction is done. Display > **Custom Logos: Pixelated / Full Detail / Do Not Use** (`custom_logos` = `pixelated` / `full` / `off`, saved; the row is there only when the game has an own or scraped logo) switches how: Pixelated (the default) shrinks it to GBA pixels, drawn from then on exactly as an extracted logo (GEN-1, GEN-5); Full Detail keeps four of its pixels to a GBA pixel, at the same size, smoothly scaled and without the LCD grid (under a HUD or in a fight, as detailed as those pictures are: two or one per GBA pixel); Do Not Use goes back to the extracted logo, for every game. The switch remakes every picture the logo is in at once. GBA DS ships none: these are the player's own files, as their overlays are.

**GEN-12. Screen placement.** With two screens, Display > **Screen Placement** (`screen_placement`, saved) puts each screen's picture (the game, the second screen's map, HUD or logo, the bezel round it) either in the middle of its screen (**Centered**, `center`, the default) or against the edge nearest the other screen (**Closest to Gap**, `no_gap`: the top screen's at its bottom, the bottom screen's at its top), so the two are as close together as they go, as on a DS, and Pokémon Pinball's table carries on across the hinge without a band of black in it. Only a picture that doesn't fill its screen's height moves (Pixel Perfect, Full Width); across, it stays centred. Which screen has the game doesn't matter (swapped, the same). With one screen the button is greyed out. With Closest to Gap, Custom overlays are looked for with `-no_gap` at the end of their names (the others' transparent area is where a centred picture goes), the Generated bezel in its usual colours where there's none, and the Generated bezel's logo, which goes in the band by the hinge, has no room there: it's on the bottom screen only, below the picture. (Issue #46; until v1.5.3's test builds, always centred.)

**GEN-13. Save states shared with RetroArch.** On Linux (ROCKNIX, BananaOS), the game list's Settings > System > **Save States** switches the pause menu's slots 0 to 9 and the resume point between GBA DS's own files (**GBA DS's Own**, the default) and RetroArch's (**Shared with RetroArch**: its `<game>.state`, `.state1` to `.state9` and `.state.auto`, in the folder RetroArch's own settings give, worked out as RetroArch does, or the one chosen with **RetroArch's State Folder**), so a game saved in one goes on in the other. Shared, GBA DS saves them as RetroArch does (its format, compressed unless RetroArch's "Save State Compression" is off) with a thumbnail beside each (`<state>.png`), and loads RetroArch's (compressed or not). A slot's label says ", RetroArch" when RetroArch saved it, "Another emulator's" when another of RetroArch's cores did (gpSP, VBA-M...: it can't be loaded, and loading it says "Saved by another emulator: can't load it"), "Can't be read" when it can't be read. The quick state stays GBA DS's, and a patched game with states of its own keeps them in GBA DS's folder. A state GBA DS saved there keeps what the second screen showed (GEN-7); one RetroArch saved doesn't have it. *By hand: RetroArch itself loading GBA DS's states and the other way round (with its GBA core set to mGBA), its thumbnails in its menu, and the folder found on ROCKNIX and on BananaOS (the tests use a stand-in RetroArch: its files are checked against BananaFront's own reader and mGBA's libretro core, byte for byte, when they change).*

**GEN-14. Turning the second screen by hand (optional, off by default).** Settings > Second screen > **Contextual toggle** (`toggle`, saved, off) turns on a hotkey (**HOME + A**, changeable under Controls > Hotkeys: `hotkey_toggle`) and a button on the second screen. In a game whose rules file has a **Toggle** row, they show the next picture of what the second screen is about: its next *page* (a status screen's three pages, the next party member: Toggle `pages`) or its other *view* (the world map or the party screen, the map or the status: Toggle `views`). They change nothing in the game and send nothing to it; the hidden copy is only asked for another picture, as it is for the first. With the toggle off, nothing about any game changes: the same pictures, at the same times. *By hand: how the button, the hotkey and the fade look and feel on the device, and that a capture that takes seconds shows the fade (the tests check the pictures at fixed frames). (checked on the device for v1.5.8: the button, the hotkey and the fade on Fire Emblem, Final Fantasy IV and FFTA, then the capture-on-press games, in the owner's test builds, Nov 21 to 22, 2026)*
- **Auto-rotate** (`auto_rotate`, on; only selectable with the toggle on) keeps timed pages turning by themselves as before, the press moving them on at once and the timer starting again from there. Off, a page stays until you press. It does nothing for `views`, which never turn by themselves.
- **What a press shows.** `pages`: the next page, in the game's own order, back to the first after the last. `views`: the other view, and back. A subject change (another unit under the cursor, another room) starts again at the first page or the default view; a refresh of the same one keeps your choice. A view stays until the context changes (a battle, a new area, a menu opening in the game, the logo).
- **The button** is the console's own, drawn by GBA DS like the bezel and not part of the game's picture: a key like the quick bar's with a double arrow on it, partly see-through, at the second screen's own pixel size (30 x 13 GBA pixels). **Show toggle button** (`toggle_button`: left, centre, right, off; left by default): in the margin under the picture where there is one, over the picture's lower edge where there isn't. It is **hidden** in games with no Toggle row; in the others it is **active** when there is another page or view to show right now, and **inactive** (dim and flat; it and the hotkey do nothing) when there isn't (Fire Emblem outside a battle, the logo, a one-page picture, a capture still being made for a new subject). Only the touchscreen takes a tap on it: with the screens swapped and the second screen on the non-touch one, there is no button and the hotkey is the way (on devices where both screens take touch, the Retroid Pocket Duo and Duo Lite, either). A tap on it is the only touch the second screen takes, and is never sent to the game.
- **The wait.** Turning to a picture that is already held (every page; a view the game keeps, **`HELD`**) shows it at once, a cut. Where the other view isn't held, a press asks for it (**`ONPRESS`**): the picture fades to black (5 frames), stays black while the game finds it, and fades back to the new one (5 frames); if it hasn't come within 2 seconds the old picture fades back and nothing changes (GEN-3). Presses while a turn is under way are ignored, not queued, and the button is inactive until it is done. A subject change, a scene or a loaded state ends a turn at once with the new default picture, no fade. Only the picture fades (not the bezel, the button or the other screen), only for a press that has to wait, never with auto-rotate.
- **Which view mode a game has** is in its Toggle row: `HELD` for the Final Fantasy games and Breath of Fire, which already keep the party picture beside the map; `ONPRESS` for Mother 3 (map and Status), The Minish Cap (map and Quest Status) and Mario & Luigi: Superstar Saga (the other brother's Bros. Info): the other view is opened on the hidden copy when the button is pressed, the picture fading to black until it is taken (up to 10 seconds, then the old view comes back). Kingdom Hearts: Chain of Memories, Boktai and Zoids: Legacy are `none` (the owner chose that for the first two, whose other screens are interactive; Zoids never has two views to turn between); Harvest Moon is `none` until its Farm Map can be drawn whole. Breath of Fire II is `HELD`, as Breath of Fire.
- **Settings in layers:** the settings are for all games; `toggle`, `auto_rotate` and `toggle_button` can also be set for one game in `states/<game>.cfg`.
- **Writing it for a new game.** A game's rules file says in its header **Toggle:** `pages` (and which rule's pages), `views` (which two, and `HELD` or `ONPRESS`) or `none`, and a game with pages or views has to say which, so the button appears and doesn't where it shouldn't. A compose function gives its pages in a stable order, the first being what shows with the toggle off, and has no timing of its own. An `ONPRESS` profile's compose takes the other view when `mapcap_alt_view()` is true, and its `altHere` says whether there is one in the situation the game is in; `tools/regress.py` stops when a case turns the toggle on for a game whose Toggle row says `none` or is missing. In a game whose Toggle row says `none` (or has none), the in-game settings' Contextual toggle, Auto-rotate and Toggle button rows are greyed out and read "Not available", so a player isn't left wondering why nothing turns.

**GEN-15. RetroArch states with zstd, or saved with the GBA BIOS (issue #78).** Shared with RetroArch (GEN-13) or loaded from its folder, a state RetroArch compressed with zstd (RZIP version 2: RetroArch 1.21 and later, when its Save State Compression asks for it) loads as one compressed with zlib does: the game goes on as it was there, and GBA DS still saves its own as RetroArch's zlib files, which every RetroArch reads. A state RetroArch's mGBA core saved with a GBA BIOS file, while the CPU was inside the BIOS (waiting for the next frame, or in an interrupt, where a game spends much of each frame), can't go on in a game GBA DS runs without that BIOS (GBA DS runs games with mGBA's built-in one), so mGBA refuses it. Loading one says so, in the pause menu ("Saved with a GBA BIOS: see Settings > System"), from the quick bar or a hotkey ("Saved with a GBA BIOS: see Settings > System > GBA BIOS.") and for a resume point ("Not resumed: ..."), instead of just "Load failed"; the log says it too (`load state: refused by mGBA: ...`). A state saved while the CPU was in the game's own code loads, whatever BIOS saved it. A file damaged or cut short is refused as "This state can't be read". Settings > System has **GBA BIOS** (Linux and Android), **Built-in** by default, where nothing differs from before: it switches to **Your Own**, the 16 KB file `bios/gba_bios.bin` in the data folder, which the player puts there (GBA DS has none and never looks for one by itself). Switching it on with no file there, or one that isn't a GBA BIOS (the wrong size, or not a BIOS), leaves it on Built-in and says why. On, every game, hidden copy and logo extraction starts with that BIOS, past its start-up logo, from the next game started; if the file goes missing, games run with the built-in one and the row says so. With it on, a state RetroArch's core saved without a BIOS while inside the BIOS is refused as "Saved without a GBA BIOS: see Settings > System" (the same way, with its own messages). The state a BIOS saved while the CPU is in the game's own code loads either way. The tests use the official BIOS (the fixtures' `bios/gba_bios.bin`) and states the harness saved with it and without it, inside the BIOS (cases `sa2-retroarch-bios-*`, `aw-bios-settings*`). *By hand: RetroArch's own states made with a BIOS file, on the device.*

**GEN-16. RetroAchievements hardcore (issue #82).** RetroAchievements hasn't approved GBA DS for hardcore, so the item is hidden until it does (`RA_HARDCORE_MENU` in ra.h; it still shows for a player with `ra_hardcore = 1`, who can switch it off); until then everything below is for that player and the testers. While it is on, for a game whose achievements are loaded: **Load State** is greyed out and no state loads however it is asked for (slots, the quick state, a RetroArch state, `--load-state`, the quick bar), rewind and fast forward do nothing (holding the fast-forward button, its on / off hotkey; the pause menu says "Fast Forward: Off in hardcore"; the setting is kept for casual play), and **Cheats** is greyed out and its cheats are not applied (they come back when hardcore goes off; their on / off marks are kept). Saving states is allowed. The quick bar's Load and the quick-load hotkey say "Not in hardcore mode (Achievements)", as the pause menu's Load State does. **Submit a Bug Report** is greyed out (the quick bar's bug button says it isn't available), since it loads an older moment into the game. Nothing is written into the game's memory: Super Mario Advance 2's SNES layout can't pan the camera with its buttons (the game's own pan buttons still work). A game that starts from a saved state or with an input script (resuming, a patch change, `--load-state`, `--input-script`) starts in casual mode, whatever was chosen, and says so; hardcore is then one switch away from the menu. The banner as the game starts and the Achievements page say which mode it is in. A game with no achievements loaded (unrecognised, patched, started offline) is played as always. By hand: each of those paths on the device (fast forward: the hold button and the hotkey, in hardcore and in casual), and a hardcore unlock in a test account, which RetroAchievements counts as hardcore only once it has approved GBA DS (until then the profile may show it as casual).

**GEN-17. Cheats from RetroArch's `.cht` files.** A game's cheat files (RetroArch's format, found by the game's title in GBA DS's own `cheats` folder and then RetroArch's folders, subfolders too) are read when the game starts: up to 512 cheats from a file, numbered `cheat0` upward (gaps in the numbers are fine, a cheat with no code is left out, one with no name is listed as "(no name)", a name is cut at 127 characters), and up to eight files. The pause menu's Extras > **Cheats** lists them with an On/Off switch each, and the count of those on is shown at the bottom. Holding Up or Down in the list moves the highlight one row at once and then steadily (the same as in the Patches list, the achievements list and the two keypads), and the list scrolls to keep it in view. A cheat's choice is kept per game (`states/<game>.cheats`, by file name and cheat name; of several cheats in one file with the same name each is remembered on its own, by its place among them, and a choices file from an older version, which doesn't say which, switches all of them), and until something is changed the file's own `cheatN_enable` values are used. The log says how many were found ("cheats: N in F file(s)") and how many are on. The tests use a file of about 500 made-up cheats with gaps, missing codes and names, a long name, a tab in a name, duplicate names, unquoted values and cheats past the 512th (case `fz-us-cheats-stress`).

**GEN-18. The language, asked on a first install (issue #92).** A system can report a language its player doesn't read (the RG DS Plus's stock Linux OS reports Chinese, and with Language on Automatic every menu, the Language row included, came up in it). So a first install (the states folder missing or empty) asks before anything else: before the game list, or, started straight into a game (EmulationStation, an Android frontend), the game starts at once and the first time the pause menu opens the question comes first, then the menu. The top screen says "Language" in every language the build has, the one in use brighter, and "Choose the language for GBA DS's menus." / "You can change it later in Settings > System." in the language in use, with the same two lines in English under them when it isn't English. The touch screen lists **Automatic** (with "System: <the system's language>"), **English** and every language by its own name, a machine-translated one with "machine translated" in its own language under it, then the Automatic help text and **Continue**. The picker starts on the setting in use (Automatic on a new install). A on another language picks it and both screens redraw in it at once; A on the one picked, START, Continue (or a tap on the one picked) keeps it; B puts back the one the screen opened with. Kept: `language` and `language_asked = 1` in `states/prefs.cfg`; until then `language_asked = 0` is there, so a first run that never reaches the game list or the pause menu asks next time. An update never asks (an older install has a states folder with files in it and no `language_asked` line, which counts as asked). Which builds ask (the owner's rule, Nov 25, 2026): releases (a version without `-dev`, the APK included) and builds made with `GBADS_LANG_ASK=1` (the main session's final dev build); never other test builds, nor the web build (the web player and State Saver, which keep no settings for a visitor who doesn't allow storage). The tests turn it on with `GBADS_LANG_ASK=1` and a system language of `zh_CN` (cases `aw-lang-first-run`, `aw-lang-first-pause`); `aw-lang-not-asked` checks a test build doesn't ask. *By hand: the stock Linux OS's own language reaching it, and a first install on the device.*

**GEN-19. Both screens on one display (issue #84).** On a single display (a tablet, a phone or a desktop window: the window is not over two panels or two displays), Settings > Screens > **One display** (`single_layout`, saved for all games) chooses between **Game only** (`off`, the default: one screen at a time, Swap Screens flips between the game and the second screen, as before), **Side by side** (`side`), **Stacked** (`stacked`) and **Both, automatic** (`auto`: side by side when the display is as wide as it is tall or wider, else stacked). With both on, the display is cut into two screens exactly as two real ones would be: the game on one and the second screen (map, HUD, logo, menus) on the other, each with its own picture, scale, bezel and overlay settings, with Swap Screens and **Screens** choosing which end the game is at (for side by side: left or right), and with the quick bar and touch working on the second one. Which layout shows follows one pattern, by what is up (issue #108): **the game** is cut as One display says; **a menu** (the pause menu and its screens: Settings, Cheats, Patches...; the game list's Settings and its screens, the update notice and the first-run language question) takes the whole display while it is open, as with Game only, and the two screens come back when it closes; **the game list** is cut as One display says, as on a two-screen device (the list on the touch screen, the selected game's preview on the other), unless the list's part would be smaller than 640x480 or wider than twice its height or narrower than 4:5 (a small display, or Stacked on a wide one). Then, and always with Game only, the game list is **the list under a short strip** (issue #84 follow-up, the owner's design, Nov 27, 2026): the selected game's details are never hidden on a single display. The strip runs across the top of the display, black, sized from the display's width as the RG DS Plus's other screen is across (a layout unit of a 256th of the width, but never so large that the strip takes more than a quarter of the display's height; 76 units tall), and holds what the other screen shows except the resume point's picture: GBA DS's logo with the GitHub link under it at the top left, the game's logo (or its name, or the "Single screen only" note) at the top right, one line under them with "Save state: picks up where you left off" or "No save state yet" on the left and the romhack / modified ROM note (GEN-8, GEN-9) on the right, then A Play / B Quit and the version number, and the ROM path under its rule when Show ROM Path is on (GEN-21). The list fills the rest, laid out as anywhere else by its part's height; on a part taller than about 1.2 times its width its sizes follow the width instead (a layout unit of a 160th of it), so the header's buttons and its "Touch or use the D-Pad" always fit. Closing a game, from the pause menu or a hotkey, comes back to the list as it was before the game. **Second screen size** (`single_size`: **Equal** 50 %, **Medium** 40 %, **Small** 30 %, saved) is how much of the display's long side the second screen gets; the game gets the rest. ## Releases and dumps

Each game's file starts with a table. Its **Releases** row lists the game codes the profile handles (the 4 letters in the ROM's header). A cartridge whose header has no code (Shantae Advance: Risky Revolution's) is filed under a code of its own and known by its CRC32 alone (`CODELESS` in `tools/make_dumps.py`). Its **Dumps** row lists, per release, every official dump of it known to No-Intro by CRC32: the cartridge, later revisions, Virtual Console and collection dumps (not prototypes, betas or demos). The one marked *tested* is the fixture the regression tests run on (`roms/CODE.zip`); the others are expected to behave the same but aren't tested. GBA DS checks the ROM a player loads against this list: the tested dump, another official one, or none of them, which means the ROM has been changed (a patch or a hack, or trimmed) or is a bad dump. It says which in its log and in bug reports. The Dumps row and `src/dumps_data.h` are written by `tools/make_dumps.py` from No-Intro's list and the fixtures: re-run it when a Releases row changes or a game is added, never edit them by hand. `tools/regress.py` won't run a case whose fixture ROM isn't the dump marked tested, so a patched ROM can't become a fixture by mistake.

A **Toggle** row says what GEN-14's toggle does in the game: `pages` (which rule's pages turn), `views` (which two views, `HELD` or `ONPRESS`) or `none`; a game whose second screen has pages or views can't leave it out.

A **Mods** row (only for games with one) lists the romhacks and patches checked to work with the profile, written by hand: per release, each mod's name and version and the CRC32 of the ROM once patched (onto the tested dump), items separated by commas (so none in the names), the ones the tests run on marked *tested*. A mod gets its own rule saying which rules hold for it and anything that differs, and its own cases, whose `rom` is the release's code, a `+` and the mod (`A88E+mlssplus-100`: the fixture `roms/A88E+mlssplus-100.zip`). `tools/make_dumps.py` puts the Mods rows into `src/dumps_data.h` too, so GBA DS knows the mod when it's loaded. `tools/romhack.py PATCH` (an IPS with `--base CODE`; a UPS or BPS finds its release itself; or an already patched ROM) is where to start with a mod someone asks for: it applies the patch, says what it changes and runs the release's cases on the patched ROM (checks that fail mean a rule broke; pictures that differ are often the mod's own content), and writes out the patched ROM and the Mods row entry to add. For players, a tested mod goes in the wiki's Supported games table, in its game's "Romhacks tested" column (never a row of its own: mods don't count as games), and its differences in the game's section there.

## Writing rules

- One behaviour per rule, in the player's terms, with where (which screen, where on it) and when (which game state).
- Rule IDs are `PREFIX-n`, numbered in order and never renumbered or reused; retire a rule by marking it *retired* and saying why.
- Every rule is either cited by a test case or marked *By hand:* with what to check and why the tests can't. `tools/regress.py --uncovered` lists rules that are neither (add a *Not covered yet* section to the game's file saying what state would cover them) and, separately, the by-hand ones to check before a release.
